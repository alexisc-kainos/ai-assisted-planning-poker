# Planning Poker — Backend API Contract

## Overview

The backend is a single WebSocket endpoint, health and read-only room status HTTP routes, and optional Jira OAuth navigation routes. Jira operations use the existing room socket, not unauthenticated HTTP import/write routes. Rooms are created implicitly: the first client to connect with a given `room` ID becomes that room's **host**; all later clients connecting with the same `room` ID join as regular users.

Room IDs are generated by the frontend (e.g. a random slug like `xk29-4plm`). How the room ID is surfaced in the URL (query param, hash fragment, path with SPA rewrites, etc.) is entirely up to the frontend team — the backend has no opinion on it.

The backend runs as a single Node.js process with all room state held in memory. There is no persistence and no shared/clustered state. A member who disconnects stays in the room as **away** and can rejoin as themselves with the reconnect token from `welcome` until the room closes (see [Rejoining](#rejoining)).

## Connecting

```
wss://<host>/ws?room=<roomId>&name=<displayName>[&deck=<deckName>][&avatar=<avatarId>][&spectating=1]
wss://<host>/ws?room=<roomId>&name=<displayName>&takeover=1
wss://<host>/ws?room=<roomId>&token=<reconnectToken>
```

| Param  | Required | Description |
|---|---|---|
| `room` | yes | Room identifier, generated by the client. Must match `^[a-z0-9]{4,32}(-[a-z0-9]{4,32})*$` (lowercase alphanumeric, segments 4–32 chars separated by single dashes, total length ≤ 128). If the room doesn't exist yet, it's created and this connection becomes host. |
| `token` | no | Reconnect token from a previous `welcome` for this room. Must match `^[A-Za-z0-9_-]{32}$`. When present, every other param except `room` is ignored and the connection rejoins as that member (see [Rejoining](#rejoining)). |
| `name` | yes, unless `token` | Display name shown to other participants. Trimmed; 1–32 chars after trim. Must be unique in the room, compared ignoring case and leading/trailing spaces (see [Unique names](#unique-names)). |
| `deck` | no | Frontend-controlled estimation deck identifier, e.g. `fibonacci` or `tshirt`. Open string with a maximum of 32 chars after trim. Blank values are treated as absent. Only meaningful on the room-creating connection; if a joiner's connection includes `deck`, the room's existing value wins. |
| `avatar` | no | Frontend-controlled avatar identifier, e.g. `capybara` or `penguin`. Open string with a maximum of 32 chars after trim. Blank values are treated as absent. The backend does not validate it against a fixed set; the frontend owns the avatar catalogue. |
| `spectating` | no | `1` joins as a spectator (see `setSpectating`). When absent the user joins as a participant. Any other value is invalid. Lets a client keep spectator mode across a reconnect. |
| `takeover` | no | `1` rejoins as the away member called `name` without a token (see [Taking over an away member](#taking-over-an-away-member)). Any other value is invalid. `deck`, `avatar` and `spectating` are ignored. |

If `room` or `name` fails validation, `token` is present but malformed, a provided `deck` or `avatar` exceeds its maximum length, or `spectating` or `takeover` has a value other than `1`, the server rejects the HTTP upgrade with `400 Bad Request` — the WebSocket never opens. If the room is already at capacity (`MAX_ROOM_USERS` (default 50) members, connected or away), a new joiner's upgrade is rejected with `403 Forbidden`; rejoining with a token or taking over is never rejected for capacity. If `name` is already used in the room, a new joiner's upgrade is rejected with `409 Conflict`.

Browsers do not expose the HTTP status of a rejected WebSocket upgrade, so clients should call `GET /rooms/:roomId` before connecting to tell the user a room is full or a name is taken, and again if the socket closes before `welcome` to explain why.

A connection without `token` or `takeover` always joins as a new member (new `id`, new `seq` at the back of the line, no vote).

### Unique names

No two members of a room, connected or away, can share a name. Names are compared after trimming and lowercasing, so `Alice` and ` alice ` clash; inner spaces are significant. A name becomes free again when the room closes, and the same name can be used in different rooms. Avatars need not be unique.

The check runs before the upgrade (`409 Conflict`). If the name is taken between that check and the socket opening, the socket is opened and then closed with `1008 "name_taken"`.

### Taking over an away member

Connecting with `room`, `name` and `takeover=1` attaches the connection to the away member with that name (same name comparison as above), as if they had rejoined with their token: same `id`, `seq`, avatar, spectating choice and current-round vote, and the original host regains host. The member gets a new reconnect `token` in `welcome`; their old token stops working (`4001 "session_expired"`).

If there is no member with that name, or they are connected, the upgrade is rejected with `409 Conflict` (or the socket is closed with `1008 "name_taken"` if that changed while it opened). No proof of identity is required: anyone with the room link can take over an away member, including the original host's role. This is an accepted risk for the beta.

### Rejoining

Every `welcome` carries a reconnect `token`, a secret unique to that member (unlike `userId`, it is never shown to other clients). Connecting with `room` and `token`:

- Restores the same member: same `id`, `seq`, name, avatar, spectating choice and current-round vote. The member is no longer away.
- If the member is the room's original host (its first member), they become host again immediately.
- If the member already has an open connection (e.g. a second tab, or a drop the server hasn't detected yet), the new connection takes over. The old one receives a `replaced` message and is then closed with `4002 "replaced"`.
- If the room no longer exists or the token isn't recognised in that room, the socket is opened and then closed with `4001 "session_expired"`; no room is created. Clients should forget the token and show the join form.

The token stays the same for the member's lifetime and stops working when the room closes, or when someone [takes over](#taking-over-an-away-member) the member.

## HTTP routes

### `GET /health`

Returns `200 OK` with body `ok`. Stateless. Used by load balancers and, on Render, for keep-warm pings while at least one room is inside its configured keep-awake window. The backend requests its public `/health` URL every 10 minutes when `RENDER_EXTERNAL_URL` is available. The default room window is 90 minutes from room creation; closing a room stops its window early, and membership or host changes do not reset it. The window is configurable with `ROOM_KEEP_AWAKE_DURATION_MS`. No keep-warm request is made when no room window is active or the public URL is unavailable.

No CORS headers are sent; the route is intended for direct browser/probe access, not cross-origin fetch.

### `GET /rooms/:roomId`

Read-only room status, used by the frontend to detect a full room or a taken name before opening the WebSocket.

```json
{
  "exists": true,
  "userCount": 2,
  "capacity": 50,
  "full": false,
  "members": [
    { "name": "Alice", "away": false },
    { "name": "Bob", "away": true }
  ]
}
```

- `roomId` is validated with the same rules as the `room` connect param; an invalid ID returns `400 Bad Request` with `{ "error": "Invalid room id" }`.
- A room that does not exist returns `200` with `exists: false`, `userCount: 0`, `full: false`, `members: []` (connecting would create it).
- `userCount` includes away members, since they keep their place.
- `members` lists every member's name and whether they are away, in join order, so the join form can flag a taken name. Anyone with the room link can see these names (accepted for the beta); ids, avatars and votes are not included.
- The result is a point-in-time snapshot; a room can still fill, or a name be taken, before the client connects, in which case the upgrade is rejected with `403` or `409`.
- CORS: if the request `Origin` is listed in `ALLOWED_ORIGINS` (comma-separated), it is echoed in `Access-Control-Allow-Origin`; otherwise no CORS headers are sent. `OPTIONS` preflight returns `204`. CORS applies to `/rooms/*` only.

### Jira OAuth navigation

Optional Jira configuration requires all of `JIRA_OAUTH_CLIENT_ID`, `JIRA_OAUTH_CLIENT_SECRET` and `JIRA_OAUTH_REDIRECT_URI`. Missing, blank or invalid configuration disables Jira without disabling manual rooms. The callback must have exactly the path `/jira/oauth/callback`, HTTPS except HTTP on `localhost`, `127.0.0.1` or `[::1]`, and no credentials, query or fragment. There is no global Jira site URL; sites come from the facilitator's authorised Atlassian resources.

- `GET /jira/oauth/start?code=<opaque-start-code>` consumes a single-use room/host-bound start code returned privately by socket `connect`. It redirects to Atlassian with expiring state and an HttpOnly, SameSite=Lax callback cookie (Secure for HTTPS). Pending authorisation expires after 10 minutes.
- `GET /jira/oauth/callback?state=...&code=...` validates the browser cookie and single-use state, exchanges the code on the backend, and checks accessible sites for classic `read:jira-work write:jira-work` scopes. Denial uses the provider's `error` query parameter. No `offline_access`, refresh token or token-bearing frontend redirect is used.
- A successful callback returns HTML with a nonce-restricted script that attempts to close the authorisation tab. If closing is refused and `connect` supplied a validated `returnUrl`, it redirects there after 250ms; a visible return link is also provided. The target must match the connecting socket's browser origin, appear in `ALLOWED_ORIGINS`, and identify the same room. HTTPS is required except loopback HTTP; URL credentials/fragments are rejected, only the room query is retained, and the app path is preserved for GitHub Pages. No token, OAuth state or code is forwarded. Status arrives over the host socket; the room also closes its popup once authorised sites are available, even before site selection. One authorised site is selected automatically; multiple sites require `selectSite`. Invalid/expired OAuth returns `400`; unconfigured navigation returns `404`. Responses use `Cache-Control: no-store` and `Referrer-Policy: no-referrer`.

Keep the room tab alive: navigate a popup or new tab, with an explicit new-tab link when the popup is blocked. Leaving the room tab can mark the facilitator away and invalidate the authorisation. OAuth start URLs/codes and cookies are private, not room links. Legacy POC HTTP import/write routes are not part of this contract and must not provide a bypass.

## Server → Client messages

### `welcome`

Sent once to a client, immediately after its connection is accepted — before any `state` broadcast.

```json
{ "type": "welcome", "userId": "user-abc123", "token": "3q2-7wEAAAAAAAAAAAAAAAAAAAAAAAAA" }
```

Tells the client its own assigned `id` and its reconnect `token`. The frontend should store `userId` and compare it against `state.users[].id` and `state.hostId` to know which user is "me" and whether it's currently host. Clients never send `userId` back to the server; the server always identifies the sender by its own connection-to-user mapping, so there's no field a client could spoof to act as another user. Keep `token` private to this browser; it is only sent back as the `token` connect param to rejoin.

### `replaced`

Sent to the previous connection when the same member opens the room in another tab or window, before the server closes that connection with `4002 "replaced"`.

```json
{ "type": "replaced" }
```

Stop accepting room actions and reconnecting automatically as soon as this message arrives, keep the saved token, and show **Use this tab instead**. Ignore further events from that socket. Do not wait for the close event: intermediaries can lose the close frame and report `1006` instead, which would otherwise cause tabs to repeatedly reconnect and take the session from each other.

### `state`

Broadcast to **all** connected clients in a room whenever anything changes (join, rejoin, going away, vote, reveal, reset, ticket change, spectating change, host change). The broadcast always includes the originator. Every `state` message is a full snapshot — clients should replace, not merge.

```json
{
  "type": "state",
  "hostId": "user-abc123",
  "revealed": false,
  "deck": "fibonacci",
  "tickets": [
    {
      "id": "ticket-1a2b3c",
      "type": "story",
      "title": "Log in",
      "description": "As a user I want to log in",
      "result": {
        "users": [{ "id": "user-abc123", "name": "Alice", "avatar": "capybara" }],
        "votes": { "user-abc123": "5" }
      }
    },
    { "id": "ticket-4d5e6f", "type": "spike", "title": "Investigate SSO providers", "description": "", "result": null }
  ],
  "activeTicketId": "ticket-4d5e6f",
  "round": 3,
  "users": [
    { "id": "user-abc123", "name": "Alice", "avatar": "capybara", "hasVoted": true, "spectating": false, "away": false },
    { "id": "user-def456", "name": "Bob", "avatar": "penguin", "hasVoted": false, "spectating": true, "away": true }
  ],
  "votes": null,
  "myVote": "5"
}
```

- `votes` is `null` while `revealed` is `false`, so vote values are never leaked early.
- Once revealed, `votes` is populated: `{ "user-abc123": "5", "user-def456": "8" }`.
- `hasVoted` lets the UI show "voted" indicators without exposing values pre-reveal.
- `myVote` is the receiving client's own current vote (or `null`), so the UI can show which card the server actually holds. It is the only per-recipient field; it never carries anyone else's value, and is the authoritative selection after a rejected re-vote.
- `deck` is included only when the room-creating connection provided a non-blank value. The backend does not choose or default the deck; when absent, the field is omitted from `state`.
- `tickets` is the room's ticket list (at most 10), in the order added. It is always present (`[]` when empty), survives host changes and is discarded with the room. Ticket `id`s are server-generated (`ticket-<hex>`) and unique within the room. Duplicate titles are allowed. `tickets[].description` is always present (`""` when none was given). `tickets[].type` is `"story"`, `"spike"`, `"bug"` or `"task"`; the frontend uses it to choose the voting deck (Story/Bug/Task use the points deck, Spike uses the day deck; the backend does not restrict vote values by type).
- `tickets[].result` is the snapshot taken the last time votes were revealed while that ticket was active, or `null` if never revealed. `result.users` lists everyone in the room at reveal time in join order, except spectators who have no vote (`avatar` omitted when absent), and `result.votes` maps those user ids to their values (non-voters are absent). It is not changed by `reset`, switching tickets, editing the ticket's title or description, or users leaving; changing the ticket's type clears it to `null`; the next reveal on that ticket overwrites it.
- `activeTicketId` is the id of the ticket currently being voted on, or `null` when none is active. Tickets never become active automatically.
- `round` identifies the current voting round. It starts at `0` and increases by one whenever the round is cleared: a successful `reset`, `selectTicket`, removing the active ticket, or changing the active ticket's type. Clients send it back with every `vote` so votes cast for an earlier round are rejected.
- `users` is ordered by join order (`seq`). `users[].avatar` is included only when that connection provided a non-blank `avatar`; otherwise it is omitted. `users[].spectating` is `true` while that user is spectating (see `setSpectating`). `users[].away` is `true` while that member has no open connection.
- A member disconnecting stays in `users[]` with `away: true` and keeps their vote, spectating choice and place towards capacity. Away members should not be shown as still to vote. No auto-reveal flip occurs. If the host disconnects, the away status and the host promotion ride the same `state` message.
- Rejoining with a token restores the same member (see [Rejoining](#rejoining)); the original host regains host.

#### Public Jira ticket metadata

Imported tickets retain the existing ticket fields and add optional metadata:

```json
{
  "id": "ticket-1a2b3c",
  "type": "story",
  "title": "Log in",
  "description": "",
  "result": null,
  "jira": { "cloudId": "cloud-id", "issueId": "10001", "key": "APP-1", "url": "https://team.atlassian.net/browse/APP-1" },
  "descriptionAdf": { "type": "doc", "version": 1, "content": [] },
  "extraFields": [{ "id": "customfield_10200", "name": "Acceptance Criteria", "adf": { "type": "doc", "version": 1, "content": [] } }]
}
```

`jira` contains public issue identity, not credentials. `descriptionAdf` retains the complete accepted Atlassian Document Format document; null/missing upstream descriptions become an empty document. On import and detail refresh, `extraFields` contains populated text fields whose names contain `description` or exactly match `acceptance criteria`, case-insensitively, excluding the standard summary and description fields. Description fields come first, and acceptance criteria appear only in the expanded view. Fields without text are omitted. Clients must treat it as optional and render nothing when absent. Imported summary limits are 255 Unicode characters; ADF is limited to 256 KiB serialized UTF-8, depth 64 (root depth 0) and 20,000 nodes. Invalid/oversized imports fail atomically, never truncate. Manual limits remain 100/500 characters.

The renderer supports formatted text, headings, lists, tables, panels, code, links and mentions without raw HTML. Unsupported/private media and embeds have labelled links to Jira. Rendering stops descending beyond depth 40 with an explicit linked fallback; this does not truncate stored ADF accepted up to depth 64. Unsafe URL protocols are not executable.

Optional `agreedEstimate` is a numeric Story deck value, separate from `result.votes`; optional `revision` is a server-managed change counter, not a client precondition. Reveal replaces the result and clears agreement; reset clears the active ticket's agreement. Selecting a ticket clears its agreement for the new round; other saved results remain. Import and agreement broadcast safe room state to everyone. All room-link holders can join and read imported content without Jira access. Disconnect/expiry does not delete imported content, results or the saved agreed estimate.

### Private Jira messages

```json
{ "type": "jiraStatus", "status": { "available": true, "connected": false } }
```

`jiraStatus` is sent only to the current facilitator on connection lifecycle changes, not broadcast to participants. `status` has required booleans `available` (server configured) and `connected` (token plus selected site), optional `site: { id, name, url }`, optional `sites: [{ id, name, url }]` while authorised but awaiting selection, and optional human-readable `reason` on invalidation. It never contains an access token or client secret.

```json
{ "type": "jira", "requestId": "req_1", "ok": true, "data": { "ticketId": "ticket-1a2b3c" } }
{ "type": "jira", "requestId": "req_2", "ok": false, "error": "Only the facilitator can use Jira" }
```

Replies go only to the requesting socket, correlated by the unchanged `requestId`. Successful `data` is action-specific (below). A valid action that fails uses `ok: false` and `error`; a malformed Jira envelope instead uses generic `error` with `message: "Invalid Jira request"`, without a correlation ID. The existing inbound rate limiter also uses generic `error`. Do not assume one status event per request or use a status event to resolve a pending request.

### `error`

Sent only to the client that triggered an invalid action. State is not changed; no `state` broadcast is sent for an `error`.

```json
{ "type": "error", "message": "Only the host can reveal votes" }
```

The room-action error vocabulary (Jira action failures are described separately):

| Trigger | Message |
|---|---|
| JSON parse failure | `Malformed message` |
| Missing or unknown `type` | `Unknown message type` |
| Known `type`, bad shape (e.g. `vote` without `value`, `vote.value` non-string) | `Invalid <type> message` |
| `vote` whose `round` is not the current `state.round` | `Vote was for a previous round` |
| `vote` while `revealed === true` | `Voting is locked until reset` |
| `vote` while spectating | `Spectators cannot vote` |
| `reveal` by non-host | `Only the host can reveal votes` |
| `reset` by non-host | `Only the host can reset votes` |
| `addTicket` by non-host | `Only the host can add tickets` |
| `editTicket` by non-host | `Only the host can edit tickets` |
| `removeTicket` by non-host | `Only the host can remove tickets` |
| `selectTicket` by non-host | `Only the host can select tickets` |
| `addTicket` when the room already has 10 tickets | `A room can have at most 10 tickets` |
| `editTicket`, `removeTicket` or `selectTicket` with an unknown `ticketId` | `Ticket not found` |
| `selectTicket` for the already-active ticket | `Ticket is already active` |
| `reveal` when already revealed | `Votes are already revealed` |
| `reset` when already reset (no votes, unrevealed) | `Votes are already reset` |
| `editTicket` on an imported ticket | `Imported Jira details are read-only` |
| Malformed Jira request envelope | `Invalid Jira request` |
| Inbound rate limit exceeded | `Rate limit exceeded` |
| Unexpected handler exception | `Internal error` |
| Heartbeat pong timeout | (no app-level `error`; socket closed with code 1011) |
| Server shutdown | (no app-level `error`; socket closed with code 1001 "server_shutdown") |
| Rejoin with an unknown token or for a closed room | (no app-level `error`; socket closed with code 4001 "session_expired") |
| Same member rejoined from another connection | Old socket receives `replaced`, then closes with code 4002 "replaced" |

The socket is kept open after any `error` except where noted.

## Client → Server messages

### `vote`

```json
{ "type": "vote", "value": "5", "round": 3 }
```

`round` is required and must be a non-negative integer; send the `round` from the latest `state`. A vote for any other round is rejected with `Vote was for a previous round`, so a vote in flight when the host switches ticket or resets is never counted against the new round. Missing or non-integer `round` is rejected with `Invalid vote message`.

`value` is a free-form string (so any deck — Fibonacci, T-shirt sizes, "?", "☕", etc. — works without backend changes). Bounds: 1–64 chars after trim, no character restrictions. Sending `vote` with a numeric value (e.g. `5` instead of `"5"`) is rejected with `Invalid vote message`. Re-voting before reveal overwrites the previous vote. `vote` after `reveal` is rejected with `Voting is locked until reset`. Voting does not require a ticket to be active, and there is no way to withdraw a vote other than `reset`.

### `reveal`

```json
{ "type": "reveal" }
```

Host-only. Sets `revealed: true` and populates `votes` in the next `state` broadcast. If a ticket is active, the revealed votes are also stored as that ticket's `result` (replacing any earlier one); with no active ticket nothing is stored. If sent by a non-host, server responds with `Only the host can reveal votes` and ignores the action. If sent when `revealed === true`, server responds with `Votes are already revealed` and ignores the action. Revealing with zero votes is allowed; `votes` will be `{}`.

### `reset`

```json
{ "type": "reset" }
```

Host-only. Clears all votes, sets `revealed: false`, and broadcasts `state` (always, even if already unrevealed with no votes — for predictability the invalid case is rejected instead, see `error` table above). Stored ticket `result`s are kept. If sent by a non-host, server responds with `Only the host can reset votes` and ignores the action.

### Ticket list

All ticket messages are host-only and broadcast `state` on success. Manual tickets have a `title` and a `description`, both plain text and trimmed by the server. `title` is required: 1–100 chars after trim, with no line breaks. `description` must be a string (it may be empty): 0–500 chars after trim, with line breaks allowed. Clients must render both as text, never as HTML. Imported Jira tickets use the separate bounded ADF contract above. `ticketId` must be a non-empty string of at most 64 chars. Bad shapes are rejected with `Invalid <type> message`.

#### `addTicket`

```json
{ "type": "addTicket", "ticket": { "type": "story", "title": "Log in", "description": "As a user I want to log in" } }
```

Appends a ticket with a new `id` and `result: null`. `ticket.type` must be `"story"`, `"spike"`, `"bug"` or `"task"`. The new ticket is not made active. Rejected with `A room can have at most 10 tickets` when the list already holds 10; removing a ticket frees a slot.

#### `editTicket`

```json
{ "type": "editTicket", "ticketId": "ticket-1a2b3c", "title": "Log in with SSO", "description": "As a user I want to log in with SSO", "ticketType": "story" }
```

Replaces a manual ticket's `title` and `description`. Both are required. Allowed on any manual ticket, including the active one. Imported title, description and type are read-only, enforced by the backend with `Imported Jira details are read-only`; host removal and selection remain available. Votes, `revealed` and the ticket's stored `result` are unchanged.

`ticketType` is optional (`"story"`, `"spike"`, `"bug"` or `"task"`; any other value is rejected with `Invalid editTicket message`). When it is omitted or equal to the current type, only the title and description change. When it differs, the ticket's type is changed and its stored `result` is cleared to `null`; if it is the active ticket, the current round is also cleared (all votes cleared, `revealed: false`, `round` incremented).

#### `removeTicket`

```json
{ "type": "removeTicket", "ticketId": "ticket-1a2b3c" }
```

Removes a ticket and its stored `result`. If it was the active ticket, `activeTicketId` becomes `null` and the current round is cleared (all votes cleared, `revealed: false`); no ticket is active until the host selects one. Removing any other ticket leaves the current round untouched.

#### `selectTicket`

```json
{ "type": "selectTicket", "ticketId": "ticket-4d5e6f" }
```

Makes any ticket in the list active and starts a fresh round: all votes are cleared and `revealed` becomes `false`. Stored `result`s of every ticket, including the newly active one, are kept until that ticket is revealed again. Selecting the already-active ticket is rejected with `Ticket is already active`.

### `jira`

All actions, including `status` and `disconnect`, are current-facilitator-only, identified by the existing authenticated member socket rather than a supplied user ID or Jira target URL.

```json
{ "type": "jira", "requestId": "req_1", "action": "import", "input": "APP-1" }
```

Every request requires `requestId` matching `^[a-zA-Z0-9_-]{1,64}$`. Clients should use unique IDs for outstanding requests. Additional fields and successful reply `data`:

| `action` | Request fields | Successful `data` |
|---|---|---|
| `status` | None | `{ status }` |
| `connect` | Optional nonblank `returnUrl`, max 2048 code units; validated against the socket origin, `ALLOWED_ORIGINS` and current room | `{ authorizeUrl, status }`; open the private, single-use start URL in another tab/popup |
| `disconnect` | None | `{ status }` with `connected: false` |
| `selectSite` | `siteId`: nonblank string, max 128 code units | `{ status }`; ID must be an authorised resource |
| `suggest` | `query`: issue-key prefix matching `^[A-Z][A-Z0-9_]*-\d*$`, case-insensitive, max 64 code units | `{ suggestions: [{ key, summary }] }`; at most 10 private, deduplicated current-search matches |
| `import` | `input`: nonblank string, max 512 code units | `{ ticketId }` plus public `state` broadcast |
| `agree` | `ticketId`: 1–64 code units; `points`: numeric member of `[1,2,3,5,8,13,20]` | `{ ticketId }` plus public `state` broadcast; no Jira write |
| `prepare` | `ticketId`: 1–64 code units; optional nonblank `fieldId`, max 128 code units | `{ fields: [{ id, name }] }` if ambiguous, otherwise `{ preview }` |
| `confirm` | `confirmationId`: nonblank string, max 64 code units | `{ written: true }` after verification, or `{ written: false, uncertain: true }` |
| `details` | `ticketId`: 1–64 code units | `{ detail: { title, descriptionAdf, extraFields? } }` plus public `state` broadcast |
| `prepareEdit` | `ticketId`: 1–64 code units; `title`: 1–255 Unicode characters, no line breaks; `description`: 0–50,000 characters; optional `extraFields`: object of up to 10 entries mapping a discovered field id to a 0–50,000 character value | `{ editPreview }` |
| `confirmEdit` | `confirmationId`: nonblank string, max 64 code units | `{ written: true }` after verification, or `{ written: false, uncertain: true }` plus public `state` broadcast |

Import accepts a case-insensitive issue key or HTTPS `/browse/KEY` URL (optional trailing slash) on the selected site's exact origin, without URL credentials. Input is trimmed and keys normalised; the API request is built from the authorised cloud ID and parsed key, never fetched from user input directly. Story, Spike, Bug and Task names map case-insensitively; other types fail. A `[SPIKE]` substring (case-insensitive) anywhere in the Jira summary overrides the mapped type to Spike regardless of the issue's actual Jira issue type, for teams without a native Spike issue type. Identity `(cloudId, issueId)` is deduplicated across the room, and the shared 10-ticket cap applies. Import does not require an editable points field and never activates the ticket automatically.

Suggestions use the connected site's `/rest/api/3/issue/picker` with a bounded key-prefix query and project-scoped JQL. The picker's own `query` text match is omitted until the prefix includes at least one issue-number digit (e.g. `AL-`), since Jira's text match on a bare project prefix with no digits returns no results even though `currentJQL` already scopes to the project; `AL-1` still passes `query` through for numeric-prefix matching. Only the current-search section is used, not history; malformed/nonmatching/already-imported keys are excluded. Results are numerically sorted by key and use plain `summaryText`, never Jira's HTML. Types are not assumed by search (sites need not have Spike configured); import still enforces the supported types. The frontend debounces typing by 300ms, ignores stale replies, and supports Arrow keys/Enter/Escape or pointer selection. Selecting only fills the field; import remains explicit. Superseded reads are aborted and do not lock mutation operations; disconnect/expiry/host change invalidates them. No additional scopes, bulk import or background synchronisation are introduced.

Agreement requires an active, revealed linked Story, Bug or Task with saved results and a matching selected Jira site. It is an explicit facilitator choice, not an average or unanimity calculation. Numbers only: coffee, strings, arbitrary values and Spike estimates cannot be written. Spike voting stays in days; Spike duration write-back is deferred to separate work.

The frontend suggests the unique most-common valid numeric vote when there is no existing explicit agreement; a tie or no numeric votes leaves the choice blank. This is only a dropdown default, not an automatic agreement or write. The single **Update Jira** control sends `agree` if the chosen value differs from the saved agreement, then `prepare`; an unchanged agreement skips the redundant save. The flow tolerates its own agreement revision broadcast before or after the preview, while external revisions, round/room/connection changes still invalidate stale previews. Field disambiguation and the explicit confirmation step remain unchanged. No wire protocol or backend authorisation rules are changed by this UI simplification.

Prepare discovers numeric story-points candidates from field schema/name and the issue's editable `set` metadata; there is no fixed custom-field ID. A single eligible field may be selected automatically. Multiple candidates require another `prepare` with an eligible `fieldId`; never choose the first match. A preview is private:

```json
{
  "preview": {
    "id": "opaque-confirmation-id",
    "issueKey": "APP-1",
    "issueUrl": "https://team.atlassian.net/browse/APP-1",
    "siteName": "Team",
    "fieldId": "customfield_10016",
    "fieldName": "Story Points",
    "currentPoints": null,
    "points": 5
  }
}
```

Display the site, issue, field ID/name, current value (`null` means unset) and replacement value before confirmation. `confirm` sends only `preview.id` as `confirmationId`, not a target or new value. The backend consumes the confirmation once, within two minutes, and checks the connection, ticket identity, revision, round, agreement, editability and current Jira value again. A new prepare replaces any previous preview. Reset, ticket switch/removal, new reveal/agreement, disconnect, expiry or facilitator change makes an old preview unusable. A changed Jira value requires fresh prepare and confirmation; no PUT is sent for that detected conflict.

Only the selected field of the bound linked issue is updated; a read verifies the result. Conflict detection is best-effort read-before-write, not atomic compare-and-swap. An uncertain reply means the write may have happened: read/reconcile with Jira before another explicitly confirmed attempt, never automatically retry. Disconnect cannot undo or reliably cancel a write already sent upstream. No background sync occurs.

`details` powers the full-screen ticket overlay: it re-fetches summary, description and matching extra fields directly from Jira, updates the room's cached ticket and broadcasts it to everyone, so any participant opening the overlay sees whatever the facilitator last fetched even though only the facilitator can trigger a live refresh. It requires the ticket to be linked to Jira and bound to the connected site (`Reconnect to this ticket's Jira site before editing` otherwise). Extra fields are discovered dynamically from fields with a plain-text schema (`schema.type === "string"`) and a name containing `description` or exactly matching `acceptance criteria`, case-insensitively; this includes project-specific names such as `Description (DSP)`. Only fields containing text are included in `extraFields`; a field need not be on the issue's edit screen to be read and displayed. Jira may return a field as a plain string or as ADF; both are normalised to ADF for display and flattened back to plain text for editing.

`prepareEdit`/`confirmEdit` write back title, description and any submitted extra fields together as a single combined change, mirroring the `prepare`/`confirm` preview-then-confirm pattern but in its own session slot so an in-flight story-points write-back and a ticket edit do not interfere with each other. A submitted `extraFields` key must match a field discovered on this issue and be editable on its edit screen, or the request is rejected with `One of the submitted fields is not editable on this issue`. `prepareEdit` re-reads the current Jira values, diffs them against the submitted fields and rejects with `No changes to write back` if nothing differs; otherwise it returns an `editPreview`:

```json
{
  "editPreview": {
    "id": "opaque-confirmation-id",
    "issueKey": "APP-1",
    "issueUrl": "https://team.atlassian.net/browse/APP-1",
    "siteName": "Team",
    "changes": [
      { "fieldId": "summary", "fieldName": "Summary", "from": "Log in", "to": "Log in with SSO" }
    ]
  }
}
```

Only fields that actually changed are listed and written; display every change's field name, old and new value before confirmation. `confirmEdit` consumes the confirmation once, within two minutes, re-checks the connection, ticket identity and revision, re-reads current Jira values and rejects with `Jira fields changed since the preview. Prepare and confirm the new values.` if any changed field's current value no longer matches what was previewed. On success the room's cached ticket (title, `descriptionAdf`, `extraFields`) is updated and broadcast to everyone, editing plain text only; there is no rich-text formatting toolbar.

Credentials, pending OAuth and confirmations exist only in backend memory for the room and authorising facilitator's member/token. Going away, host change (including promotion/restoration), token rotation/takeover, explicit disconnect, expiry/401, room closure and server shutdown clear that connection; a replacement facilitator must authorise their own account. A same-site reconnection can use retained linked tickets; another site cannot write them. No refresh token is requested/stored. Local disconnect forgets the app token, not necessarily Atlassian's durable consent; it does not revoke other rooms' independent connections. Beta no-proof away-seat takeover remains an identity risk and must not be presented as account authentication.

### `setSpectating`

```json
{ "type": "setSpectating", "spectating": true }
```

Any user (host or not) can switch between participating and spectating at any time; everyone joins as a participant unless they connect with `spectating=1`. `spectating` must be a boolean, otherwise the message is rejected with `Invalid setSpectating message`. Always broadcasts `state`, even when the value is unchanged.

- Spectators cannot vote (`Spectators cannot vote`). A host who spectates keeps every host action.
- Switching to spectating while votes are unrevealed discards that user's vote. After a reveal their vote is kept, so `votes` and the stored `result` don't change until the round is cleared.

### Disconnection

There is **no** `leave` message. When a WebSocket closes, the member is marked away (`away: true`) and keeps their `id`, `seq`, name, avatar, vote and spectating choice. If they were host, the connected member with the smallest `seq` is promoted to host; `state` is then broadcast. When no member is connected, the room closes after `ROOM_CLOSE_GRACE_MS` (default 60s) unless someone joins or rejoins first; after that, tokens for the room no longer work.

## Host behavior

- The host is whoever first connects to a given room (the original host).
- Each member is assigned a monotonic per-room `seq` (1, 2, 3, ...) at join time. "Oldest" means smallest `seq`.
- If the host disconnects, the server immediately promotes the connected member with the smallest `seq` to host, and broadcasts an updated `state` with the new `hostId`. There are no ties (every `seq` is unique within the room). If nobody is connected, `hostId` becomes `null` and the first member to join or rejoin becomes host.
- When the original host rejoins with their token, they become host again immediately.
- When nobody is connected, the room is discarded after the `ROOM_CLOSE_GRACE_MS` grace period (no persistence between sessions).
- A returning user without a token is treated as a brand-new member with a new `id`, a new `seq` at the back of the line, and no vote; they do **not** regain host.

## Notes for frontend implementation

- Hide/disable reveal & reset controls for non-host users, but treat the server's `error` response as the source of truth (UI state alone isn't a security boundary).
- Use `hostId` from `state` to determine which connected user is currently host, since it can change at runtime.
- No authentication — anyone with the room URL can join. Treat room IDs as shareable-but-unguessable join codes, not secrets.
- Implement a WS-layer reconnect strategy that sends the saved `token`; the contract guarantees `welcome` → `state` ordering on every new connection, including rejoins.
- Store the reconnect token per room (e.g. in `localStorage`) to restore the member after a refresh or reopening the link.
- Only rejoin with a stored token once the page is visible and not prerendering (`document.hidden`, `document.prerendering`). A hidden page would otherwise replace the tab the person is using, then drop and leave them away.
- Handle `replaced` immediately, without waiting for the socket to close. Only process messages and close events from the current socket, so late events cannot overwrite a resumed session.
- Treat server-initiated close codes:
  - `1001 "server_shutdown"` — backend is restarting; reconnect after a short delay (hosting provider may spin down).
  - `4001 "session_expired"` — the saved token is no longer valid; forget it and show the join form.
  - `4002 "replaced"` — this member was opened from another connection; don't reconnect automatically.
- Display names are not unique within a room. Disambiguate in the UI by `id` (or a suffix) if needed.
- The `value` string is returned to the client verbatim (no trimming by the server). Normalize in the UI if desired.

## Operational notes (for the backend team)

- Signal handling: `SIGTERM` triggers graceful shutdown — stop accepting new upgrades, iterate all rooms, send each socket a close frame with code `1001` and reason `"server_shutdown"`, then exit. Bail at `SHUTDOWN_GRACE_MS` (default 20s) if any sockets haven't closed.
- Heartbeat: server-side ping/pong via `ws`, ping every `HEARTBEAT_INTERVAL_MS` (default 30s), terminate any socket that hasn't ponged within `HEARTBEAT_TIMEOUT_MS` (default 10s). Terminated sockets run the normal `onClose` cleanup path.
- Room close: when the last connected member disconnects, a `ROOM_CLOSE_GRACE_MS` (default 60s) timer starts; a join or rejoin cancels it. The heartbeat loop also closes any room with nobody connected and no pending timer, as defense in depth.
- No CORS middleware is applied on the `/ws` route — middleware that mutates headers conflicts with the WS upgrade, and CORS isn't enforced by browsers on WebSocket handshakes.
